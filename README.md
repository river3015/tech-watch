# tech-watch

インターネット上の技術情報を定期的に収集し、日付別に蓄積して、自分用のキュレーションサイトで閲覧する仕組み。

## 目的

公式情報や技術ブログ、IT界隈で話題の読みものを継続的にチェックし、興味のある情報を効率よく把握できるようにする。毎日の情報を簡潔にまとめた自分用のサイトで、新着記事と過去のまとめを閲覧できることを目指す。通知は必要に応じて追加する。

## 収集対象の候補

- Linux Foundationなどの技術団体の公式情報
- ベンダーの公式発表、公式ブログ、技術情報
- Zenn、Qiitaなどの技術記事プラットフォーム
- メガベンチャーなどの企業が公開するテックブログ
- はてなブックマークのテクノロジー・総合、Hacker Newsなどで見つかるIT界隈の流行やカジュアルな読みもの

具体的なサイトと追加提案、初期導入の優先度は[収集対象サイトの候補](source-candidates.md)にまとめている。対象サイトは今後確定する。

## 想定する動作

1. GitHub Actionsなどで定期的に収集処理を実行する。
2. 登録した情報源から記事を取得し、前回までの履歴と比較して新着情報を抽出する。
3. 年・月・日で分けたディレクトリに収集結果を蓄積する。
4. その日の記事を選び、タイトル、出典、リンク、必要に応じた短い概要をまとめる。
5. 保存したデータから閲覧用のサイトを生成・更新し、日々のまとめと過去の記事を閲覧できるようにする。

## 構成案

定期実行 → 収集・重複排除 → 日付別保存 → 日次まとめ作成 → 静的サイト生成 → 配信、という流れを提案する。最初はデータベースを使わず、JSONとMarkdownを保存してサイトを生成する構成が扱いやすい。

保存構成：

```text
data/
  2026/
    10/
      03/
        articles.json   # その日に収集した新着記事
        digest.md       # その日のキュレーション結果
tech_watch/site.py      # 閲覧用サイト・日次まとめの生成処理
public/                 # 生成した静的サイト（Git管理対象外）
```

日付ディレクトリは日本時間の収集日を基準にする案とし、記事の公開日時と収集日時は別に保存する。同じ日の再実行では記事をマージし、URLなどを使って日付をまたぐ重複も避ける。過去のまとめは日付から閲覧できるようにする。

記事データにはタイトル、元記事URL、情報源、公開日時（取得できる場合）、収集日時、カテゴリを保存する案とする。本文全体の保存は前提にせず、短い概要と元記事へのリンクを中心に表示する。

閲覧画面は「今日のまとめ」と日付別のアーカイブを基本にする。公式の更新情報、企業の実践記事、IT界隈の話題・読みものを掲載し、カジュアルな記事も日々のまとめに含める。

GitHub Actionsで実行する場合、次回実行にも履歴を残せる保存先が必要になる。初期案は収集結果と日次まとめをリポジトリにコミットする方式。記事量が増えた段階で保存先を見直す。サイトの配信先と公開範囲は未決定。

## 現在の状態

## ローカルで使う

Python 3.11以降を使用する。追加のPythonパッケージやAPIキーは不要。リポジトリのルートで実行する。

```sh
# 収集・日次まとめ・サイト生成
python3 -m tech_watch run

# localhostで閲覧（ネットワーク上の別端末には公開しない）
python3 -m tech_watch serve
```

[http://localhost:8000](http://localhost:8000)を開く。終了はCtrl+C。`serve`は保存済みデータからサイトを生成して配信する。新規収集はしない。

```sh
# 処理を個別に実行
python3 -m tech_watch collect
python3 -m tech_watch build

# 別のポートで閲覧
python3 -m tech_watch serve --port 8080

# テスト
python3 -m unittest discover -s tests -v
```

`--config`、`--data`、`--output`で設定ファイル・保存先・生成先を変更できる。生成物は`public/`に出力し、Gitには含めない。

## 収集とキュレーションの仕様

実装済みの収集先は[config/sources.json](config/sources.json)に記載した11フィード。候補一覧の全サイトを登録したわけではなく、実取得を確認できたものから開始している。追加時は同じ形式で登録し、`enabled: false`で停止できる。

- RSS 2.0、RSS 1.0（RDF）、Atomに対応。リンク先本文の巡回は行わない。
- 初期設定は公開日時が直近7日以内、各フィードの先頭最大30件。公開日時が取得できない記事は収集する。フィードに含まれない過去記事は取得しない。
- 日本時間の収集日で`data/YYYY/MM/DD/`に保存。`articles.json`は記事、`collection.json`は最新実行の収集結果、`digest.md`は日次まとめ。
- URLのフラグメントと代表的な追跡パラメータを除去して重複判定。別URLの翻訳・転載やHTTP/HTTPSの違いは自動統合しない。同じURLが複数のフィードに載る場合は出典を統合する。
- はてな総合はキーワードでIT・ネット文化・働き方などに絞る。単純なルールなので、誤検知・取りこぼしはあり得る。キーワードは設定で調整する。
- カテゴリごとに最大5件を選び、情報源を順に回して記事が偏りにくいまとめを生成。人気スコアやAIによる順位付け・要約は未実装。画面の概要はフィードに含まれる文章を最大240文字にした抜粋。
- サイトは検索、カテゴリ切替、ピックアップ／全記事切替、日付別アーカイブに対応。収集失敗も画面に表示する。
- 各フィードは20秒のタイムアウト、最大5MiB、失敗時は1回再試行。一部失敗でも成功分を保存する。全フィード失敗時は終了コード1。複数のローカル収集処理を同時に実行しない。

## GitHub Actions

[collect.yml](.github/workflows/collect.yml)に手動実行と毎日07:17 JSTの定期収集を用意した。定期実行を有効にするには、デフォルトブランチに配置したうえで、リポジトリのActions変数`TECH_WATCH_ENABLED`を`true`に設定する。手動実行はこの変数なしでも可能。今回の作業では変数設定や手動実行は行っていない。

実行時はテスト → 収集・生成 → `data/`をデフォルトブランチへコミット・プッシュ → サイトとデータをArtifactとして7日間保存する。部分失敗の場合も成功データを保存し、最後にジョブを失敗として知らせる。全件失敗の場合はデータのプッシュを行わず、診断用Artifactを残す。

`GITHUB_TOKEN`でデータを保存するため`contents: write`を指定している。ブランチ保護などで直接プッシュできない場合はジョブが失敗する。権限の拡大や保護の解除は行わず、必要に応じてデータ専用ブランチやPR方式に変更する。

GitHubの定期実行は遅延することがあり、指定時刻の厳密な実行は保証されない。公開リポジトリでは非活動期間によりスケジュールが停止することもある。[GitHub公式のschedule仕様](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows#schedule)を参照。

[check.yml](.github/workflows/check.yml)はpush・PR時にテストとサイト生成を確認する。サイトの外部デプロイは含めていない。GitHub Pages・Cloudflare・MacBook上のローカル運用のどれにするかは引き続き未決定。
